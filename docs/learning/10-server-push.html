due 学习 06：服务端主动推送（按 uid 找到玩家）

日期：2026-06-16

本课目标：让服务端主动给某个玩家发一条消息——不是回复请求，而是服务端

自己发起。这是房间广播、"轮到你出牌"通知的基础。

1. Response 与 Push 的本质区别

到上一课为止，所有消息都是"客户端问、服务端答"：

客户端 ──请求──▶ 服务端 ──Response──▶ 客户端   （被动回复，同一路由+seq）

这一课多了一条反方向、无请求触发的通道：

服务端 ──Push(按 uid 寻址)──▶ 客户端           （主动发起，没有对应请求）
ctx.Response(msg) ctx.Proxy().Push(...)
谁发起 客户端的请求触发 服务端自己
寻址方式 沿原连接、原 seq 回去 按 uid 或 cid 主动找
典型用途 登录结果、出牌是否合法 轮到你出牌、别人出了什么、房间广播

2. 这一步加了什么

文件 改动
internal/route 新增 Notify=3 路由 + NotifyPush{Text}（S2C，无请求体）
internal/session 登录绑定成功后，调用 Push 主动给该 uid 发一条通知
cmd/testclient 注册 Notify 处理器，收取这条"没请求过"的消息

3. 关键代码：按 uid 推送

ctx.Proxy().Push(ctx.Context(), &cluster.PushArgs{
    Kind:    session.User,   // 按「用户(uid)」寻址，而不是「连接(cid)」
    Target:  uid,            // 发给哪个玩家
    Message: &cluster.Message{Route: route.Notify, Data: &route.NotifyPush{Text: "..."}},
})

Kind 决定怎么找目标：

  • session.User —— 按 uid 找。前提是这个 uid 已经 BindGate 绑定过连接，

否则网关不知道该发给哪条连接。

  • session.Conn —— 按 cid（连接号） 找，不需要登录。

为什么能按 uid 找到人？ 正是上一课 BindGate 建立的 uid ↔ 连接 对应关系 在起作用。绑定是"服务端能反向找到玩家"的前提——这两课是连着的。

4. 验证：发 2 条，收 3 条

测试客户端只发了两个请求（登录、问候），却收到三条消息：

登录响应:     玩家 1001 登录成功          ← Response（回复登录请求）
问候响应:     你好，测试客户端……          ← Response（回复问候请求）
服务端主动推送: 欢迎上线，已准备好开始游戏    ← Push（没有对应请求！）

第三条就是服务端在登录后主动推来的。没有它对应的"请求"，纯粹是服务端发起。

5. 通往房间广播

单点 Push 之外，due 还有两个放大版（同一套寻址思路）：

  • Multicast —— 一次推给多个 uid（房间里的几个玩家）。
  • Broadcast —— 推给所有在线连接。

斗地主的"某人出牌后通知另外两家"，本质就是对房间里的 uid 列表做 Multicast。 所以这一课的单点 Push，是房间广播的最小原型。

6. 本课记住三句话

  1. Response 是被动回复请求，Push 是服务端主动发起，方向相反。
  2. Push(Kind: session.User, Target: uid, ...) 按玩家 uid 寻址，靠的是 BindGate 的绑定。
  3. 多人通知用 Multicast、全员用 Broadcast——房间广播就是它们。
