测试与开发命令的划分

日期：2026-06-17

这篇不是 due 框架知识，而是从几个"测试命令该怎么放"的问题里沉淀出来的工程判断。

沉淀下来，免得以后又在同样的地方反复纠结。

1. dev.py 该管什么：编排，不是包装一切

一个开发脚本最容易长成"什么都往里塞"的大杂烩。判断该不该塞进去，有条干净的原则：

开发脚本只该管"语言工具链自己做不到的事"。

按这个原则给命令分类：

命令 需要编排吗 谁更该管
up / deps-up / server / testclient / status 要（启 Docker、等端口、跨平台） dev.py
test-integration 要（得先把依赖拉起来） dev.py
test（单元）/ vet / build 不要，就是一行 go test/go vet/go build Go 自己

那为什么 test/vet/build 还是包了一层进 dev.py？只有一个正当理由：便利。 命令行通常停在仓库根目录，包一层就能从根目录直接跑，省去每次 cd server/。 它不是新增功能，只是省一步 cd——想清楚这点，就不会把"包装"当成"必须"。

2. 单元测试 vs 集成测试：比"服务器/客户端"更有用的划分

要给"全量测试"分类，第一直觉常是按组件分（服务器 / 客户端）。但更有用的是按层次分：

单元测试 集成测试
接不接外部依赖 不接 接（Redis / etcd / Gate）
速度 毫秒，飞快 秒级，慢
跑之前要准备吗 不用 要先 deps-up
例子 card_test.go 将来测登录 / 推送的端到端

为什么不按服务器/客户端分？因为客户端现在根本没有测试套件，分出一个 test-client 是空壳——这违背 YAGNI。而单元 / 集成是马上就会用到的真实区分。

隔离手段：build tag。 集成测试文件顶部加 //go:build integration， 平时 go test ./... 默认不编译它，跑得飞快；要测端到端时才用 go test -tags integration ./...。这样单元测试永远不被慢吞吞的集成测试拖累。

3. 测试输出："成功安静，失败大声"

"信息能不能更丰富，但代码多了会不会看不过来？"——这是个普适的张力，答案是：

默认精简，详细按需打开。

Go 的默认输出就是这么设计的：

  • 通过的包：一行 ok ...（成功不啰嗦）
  • 失败的测试：自动打出完整细节（失败很大声）

这个设计天然抗增长——不管 5 个包还是 50 个包，每个包通过都只占一行。 真正会爆炸的是 go test -v：它把每个测试用例都打出来，那个才随测试数量膨胀。

所以正确做法不是"把默认调吵"，而是留一个按需开关：

dev.py test        # 精简：一包一行
dev.py test -v     # 详细：每个用例 + 子测试

这个思路以后看日志、做监控也通用：信息丰富度是个旋钮，不是常开的喇叭。

4. 一个澄清：npm 的"分开脚本"其实是什么

"我喜欢 npm 那种 dev / test / build 分开的脚本"——这里有个常见误解。

npm run dev / npm test / npm run build 不是三个独立文件，而是 一个 package.json 里的三个命名条目，都归 npm 这一个工具管。

python dev.py test / dev.py up / dev.py build 是一模一样的结构： 一个工具、多个命名子命令。所以 dev.py 已经就是 npm 模型了。真把它拆成三个 独立 .py，反而要把"等端口、启 Docker"的共享逻辑复制三份，更糟。

5. 顺带：这些图该用什么画

做这些说明图时，别用 AI 栅格生图，用代码生成的 SVG（本仓库 build_learning_html.py 就是这么干的）。原因：结构图 / 流程图 / 对照图全靠精确的文字标签，而 AI 栅格 生图恰恰在带标签的技术图上会文字模糊、标签错乱。SVG 文字精确、能进 git、能改、 缩放不糊。AI 生图擅长的是纯插画式比喻，对"讲清结构"帮助不大。

6. 测试代码现在要不要深挖？

写到这里很容易冒出一个问题：要不要停下来，专门去深入学测试代码（比如 card_test.go）？ 答案是——先专注功能逻辑（card.go），测试代码只"顺带读"，别现在把测试当独立学科深挖。

三个理由：

  1. Go 的测试几乎没有"框架"要学。 card_test.go 里全是普通 Go——循环、map、

t.Run、t.Errorf。没有 C# 那种 [TestMethod]、Mock、Fixture 一大套。所以"测试代码" 现在比被测的 card.go 还简单，没多少可深学的。

  1. 现阶段测试的价值在"思想"不在"机制"。 读测试是为了看哪些行为值得验证、边界在哪

（54 张、ID 唯一、大小王特例），这是顺着功能代码读几分钟的事，不是单独课题。

  1. 真正的测试深水区，等"有难测的东西"再学才有意义。 mock/fake、状态机测试、集成测试

脚手架——现在没有那个问题，提前学就是学完就忘（违背学习区原则）。

但有个区别要分清：

"边写边测"的纪律现在就保持（每写一块逻辑就配表驱动测试）；

"把测试当学科深挖"还不到时候。

什么时候该深挖测试（到时需求自然会拽你去学）：

触发点 会逼你学的测试技巧
写 pattern 包 牌型多 → 大表驱动，体会表驱动的真正威力
写 room / game 状态机 要"假装"网络和对手 → fake / 测试替身
测 due 路由 用 dev.py test-integration + 起真实依赖跑端到端

一句话：让测试技巧被需求拽出来，别提前囤货。

记住五句话

  1. 开发脚本管编排，不是包装一切；包 go 命令只为从根目录直接跑，是便利不是功能。
  2. 测试按"单元 / 集成"分比按"服务器 / 客户端"分更有用，用 build tag 隔离。
  3. 测试输出"成功安静、失败大声"；丰富度用 -v 按需打开，别设成默认。
  4. 技术结构图用代码生成的 SVG，比 AI 栅格生图更准、更可维护。
  5. 测试先学"思想"（验什么、边界在哪）；"机制"（mock / 集成脚手架）等真有难测的东西再深挖。
