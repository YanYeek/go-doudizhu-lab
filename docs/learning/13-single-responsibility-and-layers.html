单一职责:一个功能要不要拆开

日期:2026-06-19

起因:出牌校验的 handler 同时返回「合不合法」+「是什么牌型」。这算不算

「一个函数干了两件事」、该不该拆?借这个问题把「单一职责(SRP)」讲透。

结论先行

这样返回没问题,而且恰恰是对的。但「功能要分开」的直觉在更大的尺度上对—— 只是这里还没到拆的时候。下面分三层说清楚。

1. valid + kind 一起返回,为什么没问题

关键:它们是同一个问题的答案,不是两件事。

「这手牌是什么型 / 合不合法」本质是一次判定——pattern.Parse 一次就同时 算出了这两样:

play, ok := pattern.Parse(req.Cards)
//   |        +-- ok        = 合不合法
//   +-- play.Kind = 什么牌型

ok 和 kind 来自同一次识别。硬拆成「先问合不合法、再问什么型」,要么把 Parse 跑两遍(浪费),要么造个别扭的 API。放一个响应里,是「一次操作、一个完整答案」。

顺带:valid 其实能从 kind 推出来(kind=="非法" 就是不合法)。留着它纯粹是

对客户端友好——前端读个 bool 比拿字符串比"非法"舒服。这是 API 友好度的选择,

不是职责问题。

2. 「单一职责」到底指什么

很多人误以为 SRP = 「一个函数只返回一个值 / 只做一件极小的事」。不是。 SRP 的原话是:

一个模块应该只有一个「变化的原因」。

返回一个带多个字段的结构体,完全不违反 SRP——职责说的是「为什么会改」, 不是「返回几个字段」。

3. 这段代码其实已经分好职责了

看分层,职责早就拆开了:

层 谁 职责 因什么而改
网络适配 handlePlayCheck(game.go) 解析请求、调用逻辑、回响应 协议变了
领域逻辑 pattern.Parse(pattern 包) 识别牌型(纯逻辑) 牌型规则变了

handler 没有把牌型判定写在自己体内,而是委托给 pattern.Parse。这就是正确的 拆分:I/O 一层、逻辑一层,两个不同的变化原因,已经在两个不同的地方。

4. 「要分开」的直觉对——但时机在后面

真正该拆成多个功能的,是当「出牌校验」长大的时候。完整的出牌校验其实是 好几个独立检查:

1. 这几张牌凑成合法牌型吗?    <- 现在只有这个(pattern.Parse)
2. 现在轮到你了吗?            <- 将来(需要对局状态)
3. 这些牌真在你手上吗?        <- 将来(按 ID 查手牌)
4. 它压得过上家吗?            <- 将来(Play.Beats)

到那时,每个检查是一个独立函数(各自单一职责),handler 把它们组合起来:

// 将来的样子(示意)
if !play.valid()     { return 拒绝 }
if !isYourTurn(uid)  { return 拒绝 }
if !ownsCards(uid)   { return 拒绝 }
if !play.Beats(last) { return 拒绝 }

那才是「一个功能一个功能分开」——而且会很自然地分,因为它们确实是不同的判断、 有不同的变化原因。不要为了拆而拆,等职责真的多起来再拆。

生活类比:分诊台 vs 医生

handler 像医院的分诊台:只管登记诉求、转交给医生、把结果递回给你。 pattern.Parse 像医生:才做真正的诊断。诊断报告上同时写「有没有病 + 是什么 病」很正常——那是一次诊断的两面,不用拆成两次挂号。分诊台因「流程」变,医生因 「医学知识」变——两个变化原因,天然两个角色。

记住三句话

  1. SRP 是「一个变化的原因」,不是「一个返回值」;多字段的结果不违反它。
  2. 职责已经分好:handler 管 I/O、pattern 管逻辑,两层各因不同原因而改。
  3. 当校验长出「轮次 / 归属 / 压制」等多个检查时,每个才拆成独立函数,handler 负责组合——不要提前拆。
