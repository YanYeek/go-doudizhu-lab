# 开发与学习工作流：纵向切片、测试分层与跨平台编排

> 日期：2026-06-13
>
> 本文记录当前项目在学习节奏、前后端联调、测试方式、开发工具与部署边界上的
> 决策。Container、Gate 和 WebSocket 的概念不在此重复，分别见前两篇 due 笔记。

## 1. 当前最重要的目标

本项目首先是一个全栈游戏开发学习项目，其次才是尽快完成一款游戏。因此开发时
需要同时满足：

- 每一步能运行并观察结果；
- 问题出现时容易定位属于哪一层；
- 不一次引入过多新概念；
- 最终仍然形成可以真实部署和联机的完整游戏。

学习 due 时不需要先通读全部文档。采用渐进方式：每次学习一个框架概念，运行
代码观察行为，再把它用于真实项目。

## 2. 不先写完服务器，也不同时开发完整 Cocos

如果先完成整个服务器再接入 Cocos，可能很久看不到真实联机效果，并且协议设计
问题会集中到后期暴露。

如果从一开始同时完整开发 Go、due、WebSocket、TypeScript 和 Cocos 编辑器，
遇到错误时很难判断问题在哪一层，频繁切换上下文也会拖慢学习。

当前选择：**纵向切片开发，先用 Go 测试客户端快速反馈，再定期接入最小 Cocos
客户端。**

每个功能按以下顺序推进：

```text
Go 纯业务逻辑
    ↓
单元测试
    ↓
due 路由与消息处理
    ↓
Go 测试客户端联调
    ↓
Cocos 最小界面联调
```

## 3. 前后端推进节奏

### 第一阶段：先打通 due 核心通信链路

暂时不开发正式 Cocos 界面，依次理解：

1. Container 生命周期；
2. Gate 与 WebSocket Server；
3. Node 与消息路由；
4. 请求、响应与序列号；
5. Go 测试客户端连接、发送和接收。

完成标准：Go 客户端能够通过 Gate 请求 Node，并收到一次正确响应。

### 第二阶段：第一次最小 Cocos 联调

只创建用于验证通信的最小场景：

```text
连接按钮
发送按钮
日志文本框
```

目标不是制作正式游戏界面，而是尽早验证 TypeScript 客户端能够正确实现 due
通信协议。

### 第三阶段：按游戏功能纵向开发

后续每次完成一个可以端到端验证的小功能，例如：

1. 创建房间；
2. 加入房间；
3. 玩家准备；
4. 开始游戏与发牌；
5. 出牌与抽牌；
6. 回合切换；
7. 游戏结束。

每项功能都经过业务测试、Go 客户端测试和 Cocos 联调，而不是分别堆积大量前端
或后端功能。

## 4. 三层服务器测试策略

| 层次 | 主要验证内容 | 特点 |
|------|--------------|------|
| 单元测试 | 卡牌规则、状态机、房间逻辑 | 最快，不依赖网络 |
| Go 集成客户端 | due 路由、协议、连接与请求响应 | 快速定位服务器通信问题 |
| Cocos 联调 | TypeScript 协议兼容性与真实交互 | 最接近用户，但调试成本最高 |

大部分服务器错误应在前两层发现。Cocos 主要验证真实客户端兼容性与体验，不承担
服务器业务逻辑的主要调试任务。

## 5. 本地开发为什么使用 Python 与 Docker Compose

当前本地环境需要组合运行：

```text
Redis + etcd + due Gate + 测试命令
```

职责拆分如下：

```text
Python 开发助手
├── 检查 Python、Go、Docker 与端口
├── 调用 Docker Compose 管理依赖
├── 调用 Go 命令运行服务器
└── 组合测试、静态检查与构建

Docker Compose
├── Redis
└── etcd
```

Python 脚本只负责编排开发命令，不承载任何游戏业务逻辑，也不取代 Docker 或
生产进程管理器。

选择 Python 的原因：

- Windows、macOS、Linux 均可运行；
- 使用标准库即可进行端口等待、状态检查和条件判断；
- 相比分别维护 PowerShell 与 Shell，行为更容易保持一致；
- 当前项目后续还会加入 Gate、Node、测试客户端等组合流程。

## 6. 为什么暂不改用 Makefile 或 Taskfile

| 工具 | 优点 | 当前取舍 |
|------|------|----------|
| Shell / PowerShell | 简单直接 | 跨平台时需要维护两套逻辑 |
| Makefile | Go 项目常见 | Windows 使用体验不统一，复杂判断较笨重 |
| Taskfile | 声明式、跨平台、易读 | 每台机器需额外安装，复杂检测仍常需辅助脚本 |
| Python | 跨平台、适合编排和状态检测 | 当前采用，保持零第三方依赖 |
| Docker Compose | 非常适合管理依赖服务 | 与 Python 助手配合使用 |

如果未来团队已经统一安装 Task，可以让 Taskfile 提供更短的命令入口，但底层
复杂检测仍可继续复用 Python 脚本。

## 7. 当前统一开发入口

从仓库任意目录运行：

```bash
# 启动 Redis、etcd，并在前台运行 Gate
python scripts/python/dev.py up

# 查看服务状态
python scripts/python/dev.py status

# 运行测试、静态检查与构建
python scripts/python/dev.py check

# 停止本地 Docker 依赖
python scripts/python/dev.py deps-down
```

让 Gate 保持前台运行，是为了直接观察日志并使用 `Ctrl+C` 正常退出。开发过程中
可以保留 Redis 与 etcd，减少重复启动时间。

## 8. 跨平台开发与 Linux 部署边界

本地开发目标是让同一套命令在 Windows、macOS 和 Linux 上工作。Docker Compose
统一 Redis 与 etcd 的本地运行方式，Python 统一常用开发命令。

真实服务器通常选择 Linux，但生产环境不会长期使用：

```bash
go run ./cmd/server
```

生产环境应构建正式二进制，并由 systemd、Docker Compose 或其他容器平台负责：

- 自动启动与故障重启；
- 日志管理；
- 环境变量和密钥注入；
- 健康检查；
- 发布与回滚。

当前阶段不引入 Kubernetes。对于一个学习项目和单机部署，它会增加大量与游戏
核心无关的复杂度。

## 9. 当前阶段结论

1. 使用纵向切片推进，不先写完整服务器，也不同时开发完整 Cocos。
2. 先用 Go 测试客户端获得快速反馈，再用最小 Cocos 场景验证真实协议。
3. 使用单元测试、Go 集成客户端、Cocos 联调组成三层测试体系。
4. 使用 Python 作为跨平台开发入口，Docker Compose 管理本地依赖。
5. 本地开发脚本与生产部署严格分离，未来 Linux 部署使用正式二进制和进程守护。
